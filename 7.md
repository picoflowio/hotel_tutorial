## Catalog filtering

`HotelCatalog` loads the bundled `data/hotels.json` fixture once. Its search
filters required amenities, any accepted room type, and strict distance
cutoffs:

```javascript
const hasAmenities = amenities.every((amenity) => hotel.amenities[amenity] === true);
const hasRoomType = roomTypes.length === 0 ||
  roomTypes.some((type) => hotel.roomType.includes(type));
const nearAirport = airport == null || (hotel.nearby.airport ?? Infinity) < airport;
const nearCityCenter = cityCenter == null ||
  (hotel.nearby.cityCenter ?? Infinity) < cityCenter;
```

It is a read-only local fixture. A real implementation would make the catalog
and availability service the source of truth and validate selected hotel IDs,
not model-produced names.

## Price each stay

`PricingEngine` enumerates the requested dates and applies base-price, season,
holiday, room-type, and weekend multipliers. It filters by nightly minimum and
maximum budget and returns a price per date plus a total.

The holiday fixture is named for 2025 but compares only month and day, so its
adjustments recur in other years. Treat it as demonstration logic; production
rates need a year-aware calendar, availability checks, taxes, currency rules,
and domain-reviewed pricing policy.

---
## Keep deterministic work out of prompts

The model collects and explains criteria. The catalog, pricing engine, chart
generator, tool handlers, and validation own deterministic decisions. This
separation makes retries, testing, and later replacement of the demo backend
far more reliable.
