## Follow the normal lifecycle

A conventional conversational step usually implements `getPrompt()`,
`defineTool()`, and one or more `@Tool` handlers. On a new session, the normal
order is:

```text
onStart → onEnter → onCrossing(null) → run
  → getPrompt → selected tools → model
  → @Tool handler and transition, or onResponse
```

For a restored session, `onRestore()` runs before the normal `run` lifecycle.
On a top-level `go(TargetStep)`, PicoFlow exits the current step, enters the
target, and crosses the message into it. HotelFlow uses `onEnter()` and
`onCrossing()` in `PresentStep` specifically to replace stale context with the
current result-list task.

---
## Define and dispatch a tool in one place

`defineTool()` publishes a unique name, description, and Zod schema. `@Tool`
on the matching method selects that tool for the active step and registers its
handler:

```javascript
public defineTool(): ToolType[] {
  return [{
    name: 'chosen_hotel',
    description: 'Capture user choice of hotel',
    schema: z.object({ hotelName: z.string() }),
  }];
}

@Tool
protected async chosen_hotel(args: Record<string, any>) {
  // Validate against current hotelFound before committing a real reservation.
  return go(TerminateSessionStep).withPrompt('Confirm the booking.');
}
```

Tool names must be unique across the whole flow. Prompts describe behavior;
tool handlers validate input, invoke backend code, save state, and decide the
transition. `stay(...)` is valid only from a PicoFlow tool handler.

## Use semantic response builders

```javascript
return go(PresentStep)
  .withToolFeedback('Search criteria updated.')
  .withState({ hotelFound })
  .withMessage(this.getLastMessage());
```

`withState` saves data on the destination step. `withMessage` forwards an
existing LangChain message. `withPrompt` saves the destination's `_prompt`,
which the base `getPrompt()` returns. Use only the builders the destination
needs; data and conversational history are separate responsibilities.
