## One durable flow envelope

Each session document contains exactly one flow envelope with its registered
name, model selection, context, memory namespaces, step documents, start step,
execution sequence, token accounting, logs, status, version, and revision.

The initial HTTP `config` is persisted as flow context. Sending a different
config object with a restored `CHAT_SESSION_ID` does not reconfigure that
session; start a new session or use an explicit, validated state-changing step.

---
## Evolve stored sessions safely

Use the current restore hook when a flow or step schema changes:

```javascript
protected async onRestoreSessionDoc(
  doc: SessionType,
): Promise<SessionRestoreDecision> {
  if (doc.version > K.sessionDocVersion) return 'reset';
  if (doc.version < MIN_SUPPORTED_VERSION) return 'reset';
  // Apply an idempotent compatible migration, then return 'migrated'.
  return 'accept';
}
```

Return `accept` for a compatible document, `migrated` after an idempotent
in-place change, or `reset` when continued conversation would be unsafe. A
reset gives the caller a new session ID and leaves the old record intact.

Step and flow names are persisted schema. A rename can require coordinated
updates to steps, start state, sequence entries, memory namespaces, and
cross-step reads.

---
## Avoid conflicting turns

The engine serializes same-session work within one process and stores use
revision-based compare-and-swap. Clients should still send one turn at a time
per session. Make any external booking or payment operation idempotent before
retrying after a conflict—the session store cannot undo an external side effect.
